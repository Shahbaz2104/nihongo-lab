# Architecture & engineering decisions

Nihongo Lab is an offline-first Japanese learning app: Next.js (App Router) + SQLite, with a custom tokenizer, romaji converter, and SRS scheduler built from scratch. This document explains why each core piece exists the way it does.

## System overview

```text
Browser (client components)
  │  fetch /api/*            │  server-rendered HTML
  ▼                          ▼
Next.js App Router ──── route handlers (src/app/api/*)
  │                            │
  │  src/lib/datasets.ts       │  Prisma (SQLite, src/lib/db.ts)
  │  (react cache, server)     │  Card / ReviewLog / DayStat
  ▼                            ▼
data/*.json ─────────── dev.db (git-ignored)
  (bundled snapshots)
```

- **Server components** load and tokenize datasets (stories, vocab, kanji, grammar) and stream ready-to-render HTML.
- **Client components** handle interactivity: flashcards, quizzes, tooltips, drawing canvas, TTS playback, session flow.
- **API routes** are the only code that touches Prisma. Validation happens at the boundary; routes never leak stack traces or internal errors.
- **Data files** are plain JSON snapshots read with `react cache` so parsing happens once per process.

## Why custom tokenizer?

The core requirement is offline-first: no MeCab, no cloud NLP, no external dependencies. `src/lib/tokenizer.ts` implements a deterministic pipeline:

1. **Override map** — hand-curated readings for common inflected forms (食べました → たべる + ます, おもしろくありません → おもしろい) that a dictionary lookup can't derive from the surface form.
2. **Longest-match vocabulary lookup** against the bundled JLPT datasets — offline and fast.
3. **Particle/grammar fallback** for the rest.
4. **Kanji fallback** that splits compound kanji runs into per-character readings (normalizing dotted kunyomi like `た.べる` → `たべる`).

This is why common N5/N4 sentences tokenize correctly without any network access, and why the ~40 override entries matter: they cover the highest-frequency inflected forms the word list can't.

## Why custom romaji converter?

Romaji output (used in tooltips and kana drill answers) is generated by `src/lib/romaji.ts` from a complete hiragana/katakana mapping table — long vowels, gemination (っ), and yō-on (ゃゅょ) included. Using a library (e.g. wanakana) would pull in a dependency for a small, deterministic transformation we fully control. The converter is pure and unit-tested.

## Why SM-2 from scratch?

The scheduler (`src/lib/srs.ts`) is a faithful, deterministic SM-2 implementation: ease factor floor at 1.3, interval ramp (1 → 6 → …), lapse resets, and due-date arithmetic done in local time via `src/lib/dates.ts`. Written from scratch rather than wrapping a library because:

- The exact grading semantics (again/hard/good/easy → quality 1–5) are small enough to own and test exhaustively (17+ unit tests).
- A self-contained scheduler keeps the project educational and auditable.
- No dependency churn in the core learning loop.

## Why Prisma + SQLite?

Local-first development and simple persistence. SQLite is a single file, needs no server, and is perfect for a single-user SRS app. Prisma provides typed queries, migrations, and unique constraints (e.g. `@@unique([type, sourceId])` — the guard against duplicate cards). The schema is deliberately small: `Card`, `ReviewLog` (cascade-deleted with its card), `DayStat` (daily aggregates for the streak/history chart). Query indexes cover the hot paths (`Card.due`, `Card.level`, `ReviewLog.reviewedAt`).

## Why Web Speech API?

TTS is browser-native `speechSynthesis` with a Japanese voice preference (`src/lib/tts.ts`) — no API key, no network, works offline. This satisfies both the offline-first rule and the licensing rule ("no external speech API"). A rate parameter enables the listening mode's slow playback. The API is treated carefully: playback cancellation on unmount, a 20s safety timeout, and a voice-loading fallback.

## Why Next.js App Router?

The App Router gives a clean server/client split that maps directly onto this project's needs:

- **Server components** own dataset loading, tokenization, and Prisma — never shipped to the client (no Prisma/fs imports in client components; enforced by convention and verified in the audit).
- **Route handlers** are the thin API boundary with validation-first design.
- **Client components** own all interactivity, with `"use client"` files kept lean and importing only what they need.

The result: large dataset files never cross the wire; the client only receives the tokens/questions it renders.

## Testing strategy

- **Unit**: SRS scheduler, tokenizer (incl. all reference sentences from CLAUDE.md), romaji, review-service.
- **API**: route validation (malformed JSON, bad enums, invalid IDs, non-numeric params), seeded-deterministic quiz/listening generation, duplicate-option invariants.
- **Integration**: full queue → grade → log → day-stat flow against the real SQLite DB in tests.
- Run everything with `npm test` (Vitest), `npm run lint`, `npx tsc --noEmit`, `npm run build`.

## Known limitations

- **Web Speech voices vary by OS/browser** — synthesis quality depends on the installed Japanese voice; the app degrades gracefully (silent no-op) when unavailable.
- **Kanji stroke-order SVGs load from the network** (KanjiVG) — the only network-dependent feature; kanji drawing works offline without them.
- **ReviewLog grows unbounded** — acceptable for single-user SQLite; a 90-day retention cleanup is documented (not yet automated).
- **Datasets are bundled snapshots** — the EDRDG license requires a monthly refresh for web-facing deployment; see `scripts/update-datasets.ts` and `/about`.
